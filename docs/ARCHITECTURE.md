# Архитектура Contour CRM

Самостоятельный проект портфолио. Браузер → native Node HTTP REST → проверка cookie/Origin → доменные функции → SQLite. UI и API работают на одном origin; секреты и токены не хранятся в localStorage. Сессии хранятся в БД как SHA-256 от случайного токена; пароли — scrypt с солью.

Каждый аккаунт владеет клиентами, сделками и задачами. Перед созданием сделки сервер проверяет, что клиент принадлежит тому же владельцу. Изменения и чтение карточки проверяют owner_id. Это защищает от подстановки ID другого аккаунта. Общих организаций и команд в v1 нет.

Суммы хранятся целым числом копеек: 125000,50 ₽ → 12500050. API отклоняет дробные копейки, отрицательные суммы и превышение установленного диапазона. Это исключает хранение денежных величин как binary floating-point; форматирование выполняется в UI.

Этапы: lead → qualified/proposal → won/lost. Между открытыми этапами можно перемещаться свободно, включая возврат для уточнения. Won/lost терминальные; повторная продажа — новая сделка. Смена этапа и запись в activities выполняются в одной транзакции. Заметки дополняют историю; задачи имеют календарный срок и признак выполнения.

Ограничения: списки ограничены 200 последними записями, глобальные агрегаты считают всю базу владельца. SQLite рассчитан на один экземпляр сервера. Rate limiter хранится в памяти; перед публичным многопроцессным развёртыванием нужен общий limiter, PostgreSQL и версионированные миграции.

На интервью объясните: почему одного скрытого элемента UI недостаточно для прав; где проверяется владелец; зачем транзакция истории; почему нельзя хранить деньги в дробных рублях; чем агрегат по всей базе отличается от суммы видимых карточек.
